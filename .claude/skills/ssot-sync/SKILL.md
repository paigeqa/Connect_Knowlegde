# ssot-sync — 우리 문서를 SSOT에 맞추기

**목적**: SSOT가 정답이다. 우리 문서(`spec.md`·`qa-guide.md`)가 SSOT와 어긋난 곳을 찾아 목록으로 만든다.

**결과물**: 차이 목록 1개(`ssot-diff.md`). 문서 수정은 사용자와 같이 검토한 뒤에 한다.

에이전트를 만들지 않는다. 상태 파일을 만들지 않는다. 마지막 대조 시점은 `spec.md` frontmatter의 `ssot_reviewed`에서 읽는다.

## 이건 QA 프로세스 1단계가 아니다

혼동하기 쉬우니 구분한다.

| | 대조 대상 | 산출물 |
|---|---|---|
| 이 스킬 | SSOT ↔ `spec.md`·`qa-guide.md` | 우리 문서 갱신 |
| 프로세스 1단계 | SSOT + `spec.md` ↔ **체크리스트(테스트 초안)** | 체크리스트 수정 + 질문 도출 |

이 스킬은 1단계의 **준비물**이다. 우리 문서가 낡아 있으면 체크리스트를 낡은 기준으로 대조하게 된다.
1단계를 하려면 **체크리스트 링크가 필요하다** — 릴리즈 문서별로 Notion에 있고, 사용자에게 받는다.

## 절차 (순서 엄수)

### 1. 대조 시작 시점 확인

`spec.md` frontmatter의 `ssot_reviewed`를 읽는다. 이 날짜 **이후** 변경을 찾는다.
없으면 `extracted_from`의 rev 날짜를 쓴다.

### 2. changelog 날짜 목록만 먼저 받는다

`https://ssot.protopie.works/ko/connect/changelog`

프롬프트: **"모든 날짜를 최신순으로 나열하고 각 날짜의 항목 개수만. 날짜와 개수만, 설명 없이."**

⚠️ **한 번에 전체를 받으면 요약되면서 항목이 빠진다.** 반드시 날짜 목록을 먼저 받아 총 개수를 확인한다.

### 3. 날짜별로 원문을 받는다

대상 날짜를 **묶음당 20개 항목 이하**로 나눠 여러 번 fetch한다.

프롬프트: **"<날짜>의 항목 N개를 하나도 빠뜨리지 않고 그대로 나열. 각 항목마다 [날짜] / [변경 유형] / [문서 위치] / [변경 설명] / [코드 근거]를 원문 그대로. 요약하지 말고 각각 별도 줄로."**

받은 개수가 2단계에서 센 개수와 **같은지 확인한다.** 다르면 더 작게 쪼개서 다시 받는다.

변경 유형은 `추가` / `제거` / `정정` / `변경` 4종. **`제거`가 가장 중요하다** — 우리 문서에 `확정`으로 남아 있을 가능성이 높다.

### 4. changelog 시작일 이전 구간을 확인한다

⚠️ **changelog는 특정 날짜부터만 있다** (2026-08-17 기준 2026-07-27 시작). `ssot_reviewed`가 그보다 앞이면 그 사이 구간은 changelog에 없다.

이 구간은 SSOT **페이지 본문을 직접 확인**해야 한다. 아래 §대응표에서 우리 문서 항목이 걸린 페이지를 골라 fetch한다.

공백 구간의 존재를 결과물에 반드시 적는다.

### 5. 우리 문서에서 영향받는 항목을 찾는다

changelog의 `문서 위치`(예: `핵심 기능 › 1. Stage`)를 §대응표로 우리 문서 항목에 연결한다.

각 항목을 셋으로 분류한다.

| 분류 | 뜻 | 조치 |
|---|---|---|
| **폐기** | 우리 문서에 있는데 SSOT에서 `제거`됨 | 상태를 `폐기`로. 관련 케이스 삭제 대상 |
| 정정 | 값·이름·개수가 다름 | SSOT 값으로 고침 |
| 신규 | SSOT에만 있음 | `qa-guide.md`의 P0/P1에 확인 항목 추가 |

### 6. 우리 문서에만 있는 항목을 검증한다

`spec.md`는 "SSOT에 없는 것"만 담기로 한 문서다. 각 항목이 **아직 SSOT에 없는지** 확인한다.

⚠️ **한 페이지만 보고 "없다"고 판단하지 않는다.** 관련될 수 있는 페이지를 3개 이상 교차 확인한다.
예) Player 연결 방법 → `42-desktop` + `44-core-features` + `45-workspace` 전부 확인.

결과를 구분해서 적는다.

- **"SSOT에 없음"** — 여러 페이지 확인 후 확정. 우리 문서가 계속 들고 간다
- **"못 찾았다"** — 확신 없음. 2단계(코드) 확인 대상으로 넘긴다

### 7. 미결 질문을 처리한다

`spec.md` §4의 각 질문에 SSOT가 답을 주는지 본다.

| 결과 | 처리 |
|---|---|
| 답 나옴 | 본문(§2·§3)에 반영 + §4 "해결된 질문"에 기록 |
| 전제가 사라짐 | 질문 소멸. 소멸 이유를 기록 |
| 부분만 나옴 | 나온 부분 반영, 남은 부분만 질문으로 |
| 없음 | 2단계(코드) 또는 3단계(개발자)로 |

**SSOT 안에서 상충하는 경우가 있다.** 그때는 어느 쪽도 채택하지 말고 새 질문으로 남긴다. 상충하는 두 출처를 다 인용한다.

새 질문은 기존 `Q-N` 다음 번호를 쓴다. 번호를 재사용하지 않는다.

### 8. 결과물을 쓴다

`ssot-diff.md` (레포 루트, 작업용). 형식은 §출력 형식 참조.

### 9. 사용자와 검토한다

**여기서 멈춘다.** 문서 수정은 사용자 확인 후.

특히 이 두 가지는 반드시 사용자에게 물어본다.

- **케이스 폐기 판단** — 옛 케이스 suite를 버릴지 말지. 되돌리기 어렵다
- **"제거된 것"과 "문서가 빠뜨린 것"의 구분** — 아래 gotcha 참조

### 10. 반영 후 마무리

1. `spec.md`·`qa-guide.md` 수정
2. `spec.md`·`qa-guide.md` frontmatter의 `ssot_reviewed`를 갱신 (범위도 적는다 — 예: `2026-08-17 (changelog 2026-07-27 ~ 08-13, 68개 항목)`)
3. `AGENTS.md`의 "알려진 상태" 갱신
4. **`ssot-diff.md` 삭제** — 내용이 두 문서에 들어갔으므로
5. 커밋

## 반드시 지킬 것 (gotcha)

### 🔴 "SSOT에 없다"를 "빠뜨렸다"로 착각하지 말 것

**가장 위험한 실수다.** 실제로 한 번 틀렸다.

기능이 **코드에서 제거되면** SSOT에서도 사라진다. 이때 "SSOT가 빠뜨렸으니 우리 문서에 되살리자"고 하면 없는 기능을 테스트하게 된다.

구분 방법:
- changelog에 `제거` 항목이 있나 → 제거됨. 되살리지 않는다
- changelog에 없고 페이지에도 없나 → 판단 보류. 2단계(코드) 확인

예시: 2026-08-13에 등급 게이팅(Free/Core/Enterprise)이 코드에서 제거됐다. "플랜별 한도가 SSOT에 없다"는 빠뜨린 게 아니라 없어진 것이었다.

### 🔴 우리 문서의 `확정`을 믿지 말 것

`확정`으로 적힌 항목이 폐기됐을 수 있다. 실제로 PIN 인증이 `확정`인데 폐기된 상태였다.

`제거` 유형 항목은 우리 문서 전체를 검색해서 걸리는 것을 다 찾는다.

### ⏰ changelog fetch는 쪼개서

한 번에 전체를 받으면 요약되며 빠진다. 날짜 목록 → 날짜별(20개 이하) 순서를 지킨다. 받은 개수를 센다.

### 🔍 "없다"는 3개 페이지 이상 확인 후

한 페이지 fetch 결과의 "없음"은 false negative일 수 있다. 요약 모델이 놓칠 수 있고, 내용이 다른 페이지에 있을 수 있다.

### 📌 코드 근거를 그대로 옮긴다

`stage-access.ts:94` 같은 파일:줄 표기는 2단계(코드 확인)의 출발점이다. 요약하지 말고 그대로 옮긴다.

### 🗑 케이스를 지울 때는 이유를 남긴다

나중에 되살릴지 판단하려면 근거가 필요하다. "무효" 한 줄이 아니라 **왜 무효인지 + 언제 되살리는지**를 적는다.

## 출력 형식 — `ssot-diff.md`

```markdown
# SSOT 대조 결과 (1단계)

**작업용 문서.** spec.md·qa-guide.md에 반영이 끝나면 삭제한다.

- 대조 범위: <ssot_reviewed> ~ <오늘>
- 확인한 SSOT 페이지: <목록>
- changelog 범위: <시작> ~ <끝>, <N>개 항목 (전부 확인)

> ⚠️ 공백 구간: <있으면 명시>

## 1. 🔴 근본 변경
   (여러 항목에 연쇄되는 변경. 없으면 이 섹션 생략)

## 2. 폐기·변경된 항목 (우리 문서가 틀림)
   | # | 우리 문서 | SSOT 현재 | 근거 |

## 3. 미결 질문 처리
   | ID | 질문 | 결과 |
   ### 새로 생긴 질문

## 4. 새로 생긴 것 (우리 문서에 없음)
   영역별로 묶고 코드 근거 포함

## 5. 여전히 SSOT에 없어서 우리가 들고 있어야 할 것
   | 내용 | 우리 문서 위치 | 왜 SSOT에 없나 |

## 6. 조치 목록
   ### spec.md
   | # | 조치 |
   ### qa-guide.md
   | # | 조치 |
   ### 확인 순서 (2·3단계)
   | 우선 | 항목 | 단계 |
```
