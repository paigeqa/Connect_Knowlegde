# checklist-review — 체크리스트 교차검증 (프로세스 1단계)

**목적**: 체크리스트에 빠진 항목, 틀린 기대결과, 물어봐야 할 질문을 찾는다.

**대조 방향**: SSOT + `spec.md`·`qa-guide.md` (기준) → 체크리스트 (고칠 대상)

## 파일을 만들지 않는다

결과는 **대화로만** 준다. `checklist-diff.md` 같은 기록 파일을 만들지 않는다.

목적은 대화로 교차검증해서 **최종 체크리스트를 잘 쓰는 것**이다. 과정을 구구절절 남기는 게 아니다.

문서에 반영하는 건 **스펙으로서 중요한 것만** 이다.

| 발견 | 어디로 |
|---|---|
| SSOT에 없는 구체 수치·동작을 체크리스트에서 알아냈다 | `spec.md` |
| 테스트 범위·우선순위·보류 결정 | `qa-guide.md` |
| 답이 없는 질문 | `spec.md` §4 |
| 체크리스트 항목이 빠졌다·틀렸다 | **대화로만.** 사용자가 Notion에서 고친다 |
| 이미 통과한 항목, 진행 상황, 대조 과정 | **아무데도 안 남긴다** |

## `ssot-sync`와 헷갈리지 말 것

| | `ssot-sync` | 이 스킬 |
|---|---|---|
| 고치는 대상 | 우리 문서 | 체크리스트 |
| 산출물 | `ssot-diff.md` 파일 | 대화 |
| 언제 | SSOT가 바뀐 뒤 | 체크리스트를 쓰거나 검토할 때 |

**`ssot-sync`가 먼저다.** 우리 문서가 낡아 있으면 체크리스트를 낡은 기준으로 대조하게 된다.
`spec.md` frontmatter의 `ssot_reviewed`가 이번 스프린트보다 앞서면 사용자에게 알린다.

## 체크리스트 구조

Notion 스프린트 페이지. `notion-fetch`로 읽는다.

```
Sprint #N — connect-cloud-x.y.z / connect-desktop-x.y.z
properties: Status, date:QA:start/end, Release date, 담당 QA

📍Spec
   ├ Connect Cloud Spec (인라인 DB)  ← SSOT·피그마·개발티켓·스레드를 사람이 보려고 모은 것.
   │                                   대조 대상이 아니다. 있다는 것만 안다
   └ 개편 정리 (개발·기획이 준 변경 설명)  ← 수정 범위의 근거

📍Communication — QA Plan / QA Daily Report / QA Sign-off

📍Test Specifications
   └ Test Checklist
      └ 기능 (예: Console > Table)
         ├ 수정 범위    이번에 바뀐 것
         ├ 영향 범위    바뀐 게 건드리는 주변
         └ 회귀 범위    기존에 되던 것
              └ 환경별
                   └ - [x] 체크 항목   ← 최소 단위

📍Test Environment
📍Production Acceptance Test — 배포 후 실환경 (날짜 > 환경 > 항목)
```

상태 표기: `🟢 Passed` · `🔴 Failed` · `✅ Fixed` · `⚠️ Untested`
버그 티켓: Jira `PS-####` (`protopie.atlassian.net/browse/PS-####`)

환경 축은 보통 이 조합이다.

- `Cloud > Cloud stage`
- `Desktop > Local stage`
- `Desktop > Cloud stage`
- `Embed` (우선순위 낮음)

## 절차

### 1. 체크리스트를 읽는다

사용자가 준 Notion 링크를 `notion-fetch`로 가져온다. 링크가 없으면 요청한다.

스프린트 이름의 버전(`connect-cloud-0.3.1`)과 `date:QA:start`/`end`를 기록해둔다.

### 2. SSOT changelog에서 짝을 찾는다

**날짜를 우선으로 보고, 없으면 내용으로 본다.**

QA 기간(`date:QA:start`~`end`) 전후의 changelog 항목을 본다. ⚠️ **SSOT 반영이 QA 기간보다 늦을 수 있다** — QA가 끝난 뒤에 문서화되는 경우가 있으므로 종료일 이후 항목도 본다.

날짜로 못 찾으면 `📍Spec`의 개편 정리 제목(예: "Console 개편", "Backstage 개편")과 changelog의 `문서 위치`를 내용으로 맞춘다.

changelog fetch 방법은 `ssot-sync` 스킬의 2·3단계와 같다 — 날짜 목록 먼저, 그 다음 날짜별 원문.

### 3. 3층에 각각 다른 질문을 던진다

이게 이 스킬의 핵심이다. 층마다 대조 대상과 질문이 다르다.

| 층 | 무엇과 대조 | 던지는 질문 |
|---|---|---|
| 수정 범위 | changelog의 해당 항목 + 개편 정리 | changelog에 있는데 체크리스트에 없는 게 있나 |
| 영향 범위 | SSOT 관련 페이지 + `spec.md` | 바뀐 게 건드리는데 안 본 것이 있나 |
| 회귀 범위 | `spec.md` §5 Δ 표 + `qa-guide.md` P0·P1 | 폐기된 걸 아직 테스트하나. P0가 빠졌나 |

회귀 범위에서 특히 볼 것:

- `spec.md` §5의 Δ 항목이 회귀 범위에 반영됐나 — 레거시와 동작이 갈리는 지점이라 기대결과가 뒤집혔을 수 있다
- `qa-guide.md` P0 항목 중 이 기능에 걸리는 게 빠졌나 — P0는 출시 차단 권고 항목이다
- `폐기` 상태인 항목을 아직 테스트하고 있나 (예: PIN 입력, 등급별 한도, Upsell Modal)

### 4. 환경 축 누락을 본다

같은 기능인데 층마다 환경 조합이 다르면 물어본다.

예) Console > Table의 수정 범위에는 `Cloud > Cloud stage`와 `Desktop > Local stage`만 있고 `Desktop > Cloud stage`가 없는데, Backstage 영향 범위에는 있다.

의도적으로 뺀 것일 수 있으니 **단정하지 말고 질문한다.**

### 5. 기대결과가 맞는지 본다

체크 항목의 기대결과를 SSOT·`spec.md`와 맞춰본다. 값·이름·개수가 자주 어긋난다.

자주 틀리는 것: 컬럼 개수, 버튼 이름, 플러그인 종수, URL 파라미터 이름, 타임아웃·유예 시간 수치, 기본값.

### 6. 대화로 보고한다

이 순서로 준다. **분량은 짧게.** 발견한 것만.

1. 빠진 항목 — changelog·`spec.md`에 있는데 체크리스트에 없는 것
2. 틀린 기대결과 — 어긋난 값과 근거
3. 환경 축 누락 — 물어볼 것
4. 폐기된 걸 아직 보고 있나
5. 문서에 반영할 것 — 있으면 제안하고 사용자 확인 후 수정

발견이 없으면 없다고 말한다. 없는데 억지로 만들지 않는다.

## 반드시 지킬 것

### 파일을 만들지 않는다

기록 파일을 만들고 싶어지는 순간이 온다. 만들지 않는다. 사용자가 이 대화창에서 같이 보고 판단하는 것이 목적이다.

### 체크리스트를 대신 고치지 않는다

Notion 체크리스트는 사용자가 고친다. `notion-update-page`로 직접 손대지 않는다. 무엇을 어떻게 고칠지 대화로 알려준다.

### 이미 통과한 항목을 다시 훑지 않는다

`🟢`·`✅`가 붙은 항목은 이미 확인된 것이다. 대조 목적은 **빠진 것과 틀린 것**을 찾는 것이다. 통과 목록을 요약해서 되돌려주지 않는다.

### 지난 스프린트 이슈를 확인한다

`탐색적으로 찾은 이슈`와 `Opened(미해결)` 버그를 본다. 답 없이 넘어간 질문이 있으면 `spec.md` §4로 올릴지 물어본다.

예) Sprint #3의 "MQTT Broker는 어떤 플러그인인지?" → Slack 질문 후 답 없음 → 확인 결과 보류 결정이었으므로 `qa-guide.md`의 "다음으로 미룬 것"에 기록.

### `Untested ⚠️`를 놓치지 않는다

`⚠️`가 남아 있으면 왜 못 했는지 확인한다. 다음 스프린트로 넘길 것인지 물어본다.

### 단정하지 말고 질문한다

체크리스트를 쓴 사람이 의도적으로 뺀 것일 수 있다. "빠졌다"가 아니라 "이건 의도한 건가요"로 묻는다.
