# ProtoPie Connect Cloud — Glossary (용어 정의)
> 작성일: 2026-04-26<br>최종 갱신: 2026-05-09<br>대상 독자: PO / PM / 디자이너 / 엔지니어 모두

PRD·STRATEGY·ARCH·TECH_SPEC 본문에서 사용하는 핵심 용어를 **비개발자 관점**에서 정리. 본문을 읽다가 모르는 용어가 나오면 여기로 점프. 핵심 용어(Tenant·Bridge·Cloud·Relay)는 PRD 본문에서 inline으로 한 줄 설명됨.

---

### A-1. Tenant (테넌트) — 가장 중요한 개념
> **Tenant = SaaS에서 데이터·설정·과금·권한이 서로 격리되는 가장 큰 경계 단위.**

비유: 아파트의 한 "세대" — 같은 건물 안에서도 세대끼리 벽으로 분리되고 관리비도 세대 단위.

### 30초 만에 이해하기 — 김디자이너의 하루

| 상황 | 김디자이너의 Tenant 소속 |
|---|---|
| **혼자 쓸 때 (단독)** | 가입하면 본인 1인 팀 "김디자이너의 작업실" = Tenant 1개 자동 생성. 본인 결제, 본인 Pie만 들어있음 |
| **친구와 함께 (2인 팀)** | 김디자이너의 작업실에 박디자이너 초대 — 여전히 같은 Tenant. 결제는 owner 김디자이너. 박디자이너 본인의 별도 작업실은 다른 Tenant |
| **여러 작업실 동시 소속** | 김디자이너는 본인 작업실 + 박 작업실(초대받음) = **여러 Tenant 동시 소속**. UI에선 좌측 상단 워크스페이스 스위처로 전환 (Slack과 동일) |

**핵심 메시지 3개**:
1. **한 사람이 여러 Tenant에 동시 소속** (Slack 워크스페이스처럼)
2. **결제는 Tenant 단위** — owner가 누구인가에 따라 결제자 결정
3. **Tenant 사이 데이터는 절대 안 섞임** — Pie·플러그인·세션 모두 Tenant 경계 안에서만 보임

### Beta 모델
**1 Team = 1 Tenant** (Addon 구매 단위가 Team). Team 1개 = Tenant 1개 (사실상 Tenant ≈ Team).

### Tenant 단위로 격리되는 것
사용자 계정 / 팀·멤버 / **Room** / 플러그인 / Pie / Relay 방 / 과금·결제 / 감사 로그 / 사용량 통계 — **모두 Tenant 경계에서 분리**. Tenant 안에서는 다시 **Room 단위로 가시성·멤버십이 한 번 더 격리**됨 (디스코드 채널 모델).

### Tenant 격리는 "인프라 격리"가 아니다
본 PRD의 Tenant 격리는 **애플리케이션·비즈니스 레벨** (DB 컬럼·코드 분리, 과금 경계). **진정한 인프라 격리(전용 VPC·DB·클러스터)는 이번 범위 아님**. 모든 Tenant가 같은 ECS·DB·Redis 공유, DB 컬럼 격리로만 분리.

### UI 카피 정책
"Tenant"는 **내부 기술 용어**. 실제 사용자 화면에는 "Workspace" 또는 "Team"으로 노출.

### 자주 혼동되는 점
- **Tenant ≠ User**: Tenant에 멤버가 초대받으면 여러 명이 한 Tenant 공유
- **Tenant ≠ Team**: Tenant 단위가 결제 단위, Team은 그 안의 작업 그룹
- **Tenant = 격리 경계**: "이 데이터를 누구에게 보여줄 수 있는가"의 바깥 울타리

> 데이터 모델 세부(엔티티 관계·membership 테이블·token lifecycle·Tenant 전환 state machine)는 [SSOT §5](https://app.notion.com/p/35645184b5da80b4b5dfce0793c2ff26) 에서 다룬다.

### A-2. Team (팀)
> **Team = Tenant 안에서 플러그인·프로토타입·협업 자원을 함께 쓰는 작은 그룹.**

**비유**: 회사 안의 부서·프로젝트 그룹.
**이 제품에서**:
- 가입 시 자동으로 1인 "기본 팀"이 생성됨 (혼자 있다가 친구 초대로 확장 가능)
- 한 사용자가 **여러 팀에 동시 가입 가능** (본인 팀 + 친구 초대받은 팀 등)

**팀 단위로 공유되는 것**: 플러그인 라이브러리, 멤버 명부, 결제 컨텍스트. **실제 작업 자원(Pie·Relay 세션·플러그인 인스턴스)은 Team이 아니라 Room 단위로 묶인다** — 디스코드 카테고리(Team) 안에 채널(Room)이 있는 모델.

### A-3. Room (룸) — Tenant 안의 영구 작업 공간
> **Room = Tenant 안에서 사용자가 만드는 영구 작업 공간.** Pie·플러그인·Relay 세션·멤버를 자기 단위로 묶음.

비유: **디스코드 채널**, **노션 페이지**, **슬랙 채널**.

### Team만으론 부족한 이유
Team은 **결제·소속**의 단위지, 작업 그룹의 단위가 아님. 한 사람이 같은 Team 안에서도 여러 작업을 하고 그중 일부만 동료에게 공유하고 싶음:
- B2C: "혼자 실험하는 Pie" + "친구와 같이 보는 Pie" + "외주 클라이언트에 임시 공유한 Pie" — 같은 Team인데 멤버가 다름
- 같은 팀이라도 협업 단위가 다른 작업이 필요한 경우 — 팀 전체 자료 / 일부 멤버만 보는 TF / 본인 실험 공간

→ **Room이 그 단위**. Team이 "회사·부서"라면, Room은 "프로젝트 공간·채널·플레이그라운드".

### Room 2종

| 종류 | 가시성 | 주 사용 |
|---|---|---|
| **Private** | 본인만 | 혼자 실험·드래프트. 가입 시 "내 작업실" 1개 자동 생성 |
| **Shared** | 초대받은 Tenant 멤버 | 협업 프로젝트, 클라이언트 임시 공유 |

> **Tenant 멤버 ≠ Room 멤버**. Tenant에 들어왔다고 그 안의 모든 Room이 보이는 게 아님. Room마다 명시적 멤버십 별도.

### 멤버 역할
- **owner**: Room 만든 사람. 멤버 초대·삭제·Room 삭제
- **editor**: Pie 추가·수정, Relay 세션 시작
- **viewer**: 시청·인터랙션만 (수정 불가). stageview 게스트도 이 역할

### Room 안에 들어가는 것
Pie 파일 / 활성화된 플러그인 / Relay 세션 / stageview 채널 / 활동 로그 — 모두 Room 단위로 격리.

### 비교 (다른 SaaS 도구)

| 우리 | 디스코드 | 노션 | 슬랙 |
|---|---|---|---|
| Tenant | 서버 | 워크스페이스 | 워크스페이스 |
| Team | 카테고리 | (Team 기능) | 채널 그룹 |
| Room | 채널 | 페이지 | 채널 |

Connect의 Room은 **디스코드 채널**에 가장 가깝다 — 영구·명시적 멤버십·자원 묶음·세션은 그 안에서 일시 발생.

### Room 관련 자주 혼동되는 점
- **Room ≠ Relay 방**: Relay 방은 Room 안에서 일시적으로 시작되는 통신 세션. Room은 영구 컨테이너
- **Room ≠ Team**: Team은 결제·소속 단위. Room은 작업·가시성 단위
- **Room ≠ Tenant**: Tenant는 회사·과금 경계. Room은 그 안의 채널

> 데이터 모델·F-ROOM 요구사항은 §6-2 참고. UI 카피는 "Room" 또는 "Workspace"로 노출, "Tenant"는 절대 노출 금지.

### A-4. User (사용자)
> **User = 로그인하는 한 명의 사람.**

**관계** (확정):
- User ↔︎ Tenant = **N:M** (한 사용자가 여러 Tenant에 동시 소속 가능)
- 본인이 만든 팀 + 초대받은 팀 등 여러 Tenant에 동시 멤버일 수 있음
- 같은 사용자가 다른 Tenant에서는 다른 역할(role)을 가질 수 있음
- 사용자는 작업 시 **현재 컨텍스트(Tenant)를 선택**하여 작업 (Slack 워크스페이스 전환 UX)

### A-5. Device (디바이스)
> **Device = 사용자가 Bridge 앱을 설치한 PC/노트북 1대.**

**예시**: 김디자이너가 회사 맥북 + 집 데스크탑에 각각 Bridge 앱을 설치하면 → Device 2개 등록.
**왜 필요한가**: 노트북 분실·퇴사 시 사용자 전체를 막지 않고 **해당 디바이스만 차단** 가능.

### A-6. Bridge (브릿지 앱)
> **Bridge = 사용자 PC·서버에서 동작하는 로컬 에이전트.** Arduino·MIDI·USB 등 하드웨어와 통신, 플러그인 IDE 제공, Cloud와 연결해 원격 협업.

### Bridge 통신 모드 — hybrid

| 모드 | 동작 | 사용 시점 |
|---|---|---|
| **로컬 서버 단독** | Bridge 자체가 로컬 서버 역할. Cloud 연결 없이 LAN에서 시청자 디바이스와 통신 | 오프라인 환경, 보안 격리, 사내 LAN 시연 |
| **클라우드 통신** | Cloud Relay 경유 분산 협업 | 분산 하드웨어, stageview 글로벌 시청, 원격 시연 |

**hybrid**: 두 모드 동시 지원. 인터넷 단절 시에도 로컬 모드로 작업 지속.
**Bridge 형태**: GUI 데스크톱 앱 (macOS / Windows / Linux). Electron 셸로 패키징.

> 빌드 보호(코드 난독화·라이선스 우회 차단)는 §6-4 Bridge 앱 요구사항 참고.

### A-7. Cloud (클라우드 서버)
> **Cloud = ProtoPie가 운영하는 중앙 서버.**

AWS에서 동작하며, 사용자 인증·데이터 저장·팀 자료 공유 및 협업 메시지 중계·플러그인 격리 실행을 담당.

### A-8. Relay (릴레이)
> **Relay = 여러 디바이스 간 실시간 메시지를 주고받는 통신 채널.**

**비유**: 음성 통화의 교환기.
**예시**: 김디자이너가 자기 PC에서 프로토타입을 실행하면, 박팀장의 휴대폰에서 동시에 같은 화면을 보고 조작 가능. 두 기기 사이의 메시지 전달 = Relay.

### A-9. Plugin (플러그인)
> **Plugin = 사용자가 작성하거나 가져온 작은 프로그램.** ProtoPie 프로토타입에 외부 기능 연결.

예시: "Arduino 버튼 → 화면 전환" / "인터랙션 → IFTTT 집 조명" / "Google Maps API 호출"

### 실행 위치 — Bridge
Beta 플러그인은 **사용자 PC의 Bridge에서 실행**. Arduino·MIDI·USB 등 로컬 하드웨어 접근, 또는 MQTT·REST API·IFTTT 등 네트워크 기반 작업 모두 Bridge 안에서.
- Bridge IDE에서 **사용자가 직접 작성** 가능
- **Tenant 라이브러리로 공유**, **Room 단위로 활성화**

### A-10. SaaS (Software as a Service)
> **SaaS = 사용자가 직접 설치/관리하지 않고, 인터넷으로 접속해 쓰는 소프트웨어 서비스.**

보통 월/연 구독제. 예: Notion, Slack, Figma.
**현재 ProtoPie Connect와의 차이**: 현재는 사용자 PC에 데스크톱 앱을 설치해 쓰지만, SaaS화되면 일부 기능을 웹에서 쓰고 회사 단위로 구독 과금 가능.

### A-11. RBAC (Role-Based Access Control)
> **RBAC = 사용자의 역할(관리자/멤버/뷰어 등)에 따라 가능한 작업을 제한하는 권한 모델.**

**예시**: 팀 관리자는 멤버 초대 가능 / 일반 멤버는 못 함.

### A-12. SLA (Service Level Agreement)
> **SLA = 서비스가 얼마나 안 끊기는지에 대한 약속 수준.**

| 수준 | 한 달 허용 다운타임 | 한 해 허용 다운타임 |
|---|---|---|
| 99.0% | 약 7시간 | 약 3.6일 |
| 99.9% | 약 43분 | 약 8.7시간 |
| 99.95% | 약 21분 | 약 4.4시간 |
| 99.99% | 약 4분 | 약 52분 |

**Beta는 외부 SLA 약속 없음** — 최선의 노력.

### A-13. Multi-tenancy (멀티테넌시)
> **Multi-tenancy = 하나의 서비스 인프라 위에서 여러 Tenant를 동시에 운영하는 방식.**

**비유**: 한 아파트 건물에 여러 세대가 살듯, 한 서비스 인프라에 여러 사용자·팀이 함께 들어있음.

### A-14. Audit Log (감사 로그)
> **Audit Log = "누가 언제 무엇을 했는지" 기록하는 로그.**

**왜 필요**: 보안·컴플라이언스를 위해 "지난 30일간 누가 어떤 플러그인을 업로드했나?" 같은 추적 가능.

### A-15. Addon / Entitlement (애드온 / 사용 권한)
> **Addon = ProtoPie Cloud에서 추가 구매할 수 있는 옵션 상품. Entitlement = "이 Tenant가 어떤 Addon을 구매했는가"의 권한 기록.**

### Addon 판매 모델
- ProtoPie Cloud는 기본 프로토타입 도구. 그 자체로 사용 가능
- **Connect는 Team 단위로 별도 Addon 구매**. 그 팀(=Tenant)의 모든 멤버에게 Connect 사용권 부여
- **Entitlement는 사용자 단위가 아니라 Tenant 단위**

### 같은 사용자도 Tenant마다 사용 여부가 다름
- 김디자이너가 Team A(Connect 구매됨)와 Team B(미구매) 양쪽에 소속
- Team A에서 작업할 땐 Connect 사용 가능
- Team B에서 작업할 땐 Connect 사용 불가
- 즉 **"이 사용자는 Connect를 쓸 수 있나?" 가 아니라 "이 사용자가 현재 Tenant에서 Connect를 쓸 수 있나?"** 가 올바른 질문

### Tenant 내부의 권한 통제 (RBAC)
Tenant가 Connect를 구매했더라도, **그 안의 모든 멤버가 모든 작업을 할 수 있는 건 아님**:
- 누구나 사용 가능한 작업: 프로토타입 실행, Relay 방 참여 등
- 특정 권한 필요한 작업: 플러그인 업로드/삭제, 멤버 초대, 결제 정보 변경 등 — Admin·Owner만 가능

→ "이 멤버가 어떤 행위를 할 수 있는가"는 **사용자의 Tenant 내 역할(role)** 로 결정됨.
**비유**: Microsoft 365의 Copilot Addon. 회사가 Copilot 라이선스를 사면 직원들이 쓸 수 있지만, 누가 어떤 정책을 변경할 수 있는지는 직원 역할에 따라 달라짐.

### A-16. ECS (AWS 배포 환경)
- **AWS ECS**: 간단한 컨테이너 실행 서비스. Beta는 ECS 단일 환경에서 운영.

> 자세한 인프라 세부사항은 별도 문서.
